# Merchant fulfillment local slice

This extends existing online stock and payment authority. It never creates a second catalogue, stock counter or account. Parent Order remains the customer's accepted charge; MerchantOrder freezes one tenant/location responsibility and MerchantOrderSet reconciles all child money exactly.

## Creation and recovery

`MERCHANT_FULFILLMENT_ENABLED=true` opts NEW fully mapped paid electronic marketplace orders into child fulfillment. Default is off. Cash, COD, unpaid, unlocated/mixed legacy, direct website, POS and venue remain with their existing workflows. No backfill or historical inference. New line IDs are assigned only inside the original order transaction. An allocation error rolls back parent, holds and children together.

Shipping/tax allocation uses deterministic largest-remainder proportional allocation of the ALREADY accepted parent charges, policy `merchandise-weighted-v1`; it adds no fee. The complete merchandise/revenue/discount snapshot must reconcile before creation. New collections declare no automatic index migrations. Existing models/rollups remain unchanged.

After acceptance, turning off the creation flag does not disable child recovery. Each merchant action uses JWT tenant authority, existing orders permissions, the actual saved group and exact operation key/version. Tenant/location-scoped holds pass through the existing stock transition with unchanged batch, rollup and movement commands. Version1 ship/cancel affects all lines in that one child. New optional version2 also requires `MERCHANT_QUANTITY_FULFILLMENT_ENABLED=true`: per-original-line holds and exact unit-range shipments/cancellations reuse the same physical stock primitive. Missing-version historical children stay version1; no backfill or conversion. The whole-parent status/refund/legacy cash/delivery routes refuse managed parents.

## Refund boundary

Merchant staff can reserve an own merchandise refund. Only platform admins execute or reconcile, with cross-tenant audit. Supported sources are the existing allocated Stripe/platform or Paystack/platform receipt with exact original customer, reference, currency, amount and posted tenant merchandise/receivable/commission journal. No new provider/account is chosen. Executing requires explicit `MERCHANT_REFUNDS_ENABLED=true`; credentials remain the original platform provider server secret; Paystack additionally requires default-off `MERCHANT_PAYSTACK_REFUNDS_ENABLED=true`. This is not provider approval or deployment certification.

The child and parent budget reserve together; a stable request key prevents repeated reservation. Before transport the reserved source is checked again. Provider evidence must name the exact allocation, parent and merchant, original payment intent, amount and currency. `MerchantRefundEvidence` consumes a provider/account/refund ID once using Mongo's intrinsic unique `_id`. A successful verified response, original-account journal reversal, budget settlement and parent payment status commit together. Provider/local uncertainty retains the reservation; execution cannot resubmit it. Platform operators may supply an existing provider refund ID for read-only retrieval and exact verification. Monetary refunds never return goods or reverse COGS/inventory.

Shipping/tax refunds, Korapay/wallet/gift refunds and physical disposition remain unsupported here. Paystack binds the original canonical numeric transaction identity, persists the validated create refund ID before authenticated fetch, and settles only `processed`; pending/unknown outcomes retain reservation and cannot resubmit. [Completion evidence](../../../docs/superpowers/plans/global-phases/phase-d-finance-completion.md) records actual protocol/Mongo/JWT/UI checks. Protected `/:id/refund-readiness` exposes exact own accepted components and explicit source/shipping/tax/payout/physical-goods review gates; private provider identities/costs/shares stay excluded. A paid child with shipping/tax allocation cannot be fully cancelled through merchandise-only refund; explicit financial review is required. A pre-shipment refund reservation or completed refund blocks shipping, so money and goods cannot both leave silently.

For V1, `goodsCancellation.cancelGoodsAccounting({parent,child,actor,session})` runs before owned stock release in that same transaction. It reconciles the original accepted cost with the tenant's posted COGS journal, freezes private line residual ownership in MerchantGoodsCancellation, then posts only the cancelled child's debit1200/credit5000 once. Missing/inconsistent positive-cost evidence blocks release; genuine legacy zero cost with no cost journal remains valid. Current SKU/batch cost is never substituted and monetary refunds still never restock or reverse COGS.

New V2 quantity orders additionally require `MERCHANT_QUANTITY_FULFILLMENT_ENABLED=true`; V1 whole-group rules above remain V1-only. `quantity/refunds.request(childId,{lines:[{line,ranges:[{start,quantity}]}],expectedVersion,idempotencyKey,reason},actor)` binds exact zero-based original unit ranges to the existing Stripe receipt/budgets. Server derives money/shares; reserved/refunded financialBlocks protect those ranges from shipment. A verified common settlement marks only its blocks refunded and advances version. V1 arbitrary-amount requests refuse V2. `quantity/goodsCancellation.cancelQuantityGoodsAccounting({parent,child,lines,allocationId,actor,session})` verifies refunded coverage and never-consumed holds, then reverses exact original cost ranges before release. Its journal and immutable cancellation evidence share the canonical cancellation ObjectId. Private basis helpers and costs are never operational DTO fields. Detailed provider gates, exports and local evidence: [financial continuation](../../../docs/superpowers/plans/global-phases/phase-d-refund-provider-extensions.md).

## Queue and delivery

`/api/merchant-orders` serves tenant-private operational records; `/merchant-orders` is the admin queue. Line labels and recipient/address are allowlisted own-record projections; provider/account, private shares, costs and sibling lines are excluded. Exact action-key retries survive an uncertain network result. Platform refund controls request execution or verify existing evidence; no browser declares provider success.

Pickup quotes/bookings/tracking live separately under `deliveryProviders/` and `/api/merchant-delivery`. They never consume stock or impersonate a courier proof. Reviewed zero-shipping pickup remains supported. A separate opt-in reviewed local-dispatch package now binds original shipping budget, own approved driver/trip and exact V2 goods allocation; see `docs/superpowers/plans/global-phases/phase-d-local-dispatch.md`. The separate default-off `deliveryProviders/external/` parcel candidate uses original manual-shipped allocations and the same accepted shipping budget; provider observations never confirm canonical goods automatically. Read its README for reviewed scope and certification limits. See `../deliveryProviders/README.md` and `docs/superpowers/plans/global-phases/phase-d-delivery.md`.
